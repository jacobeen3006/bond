<objective>
Make approval policy a per-session property of the gate rather than a property of tools: the session's mode decides escalation, the deny floor below it decides everything else, and a denial provably touches nothing on disk.

**User story (MVP enrichment):** **As a** HALO user, **I want to** choose per conversation how much my agent may do without asking, **so that** a cautious session and a fast session differ by one setting instead of by which tools happen to check that setting.

Purpose: GATE-07 is the requirement easiest to bend into per-tool behavior; this plan keeps the mode in one place (`policy/modes.py`), reads it once per batch from the session's own row, and proves the three modes plus the floor with behavior tests through the loop. It also settles the persistence story (row survives restart, stays inside the session) that Phase 7's child-session inheritance and Phase 10's approvals UI will build on without changing the gate.
Output: `halo_agent/policy/modes.py`, the snapshot wiring, the session-mode writers, and `tests/policy/test_approval_modes.py`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| session state -> gate snapshot | Per-session policy enters the pure evaluator once per batch; anything it can reach is policy |
| mode -> escalation outcome | The only lever a user has; if it reached the floor, the floor would be advisory |
| session row -> other sessions | A grant or mode that crossed sessions would silently widen another conversation's permissions |
| handler -> disk | Only an allowed call may reach it, and a denied call must leave the workspace byte-identical |
