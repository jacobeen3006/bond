<objective>
Prove the phase's architecture end to end on the first slice: one tool name resolves through the registry, is judged by a pure gate, is dispatched only if allowed, and leaves a decision row the persisted tool row references — with a denied call proven to have touched nothing on disk.

**User story (MVP enrichment):** **As a** HALO user, **I want to** every tool call my agent makes to be judged and recorded before it can run, **so that** no capability exists that a policy cannot see or stop.

The ROADMAP Phase 4 goal ("Every tool decision passes exactly one registry and one pure policy gate before any backend runs, with deny as the default") is outcome-shaped, not a user story; the sentence above restates it faithfully and adds no scope.

Purpose: this is the tracer. It wires every layer Phase 4 touches — ownership manifest, loader, registry, gate request/decision types, evaluator, batch admission, loop ordering, migration DDL, store writers — in one runnable path, so an architectural dead end (wrong gate placement, a denial that lies about `dispatched`, a decision row no row references) is caught after one commit instead of after six plans. Production quality, kept for good: real error handling on the one path, no stubs, no batch fan-out, nothing that later needs an architectural change.

Output: `contracts/tool-ownership.json`, `halo_agent/tools/`, `halo_agent/policy/`, `halo_agent/adapter/admission.py`, the additive migration with its guard trigger, the loop insertion, and two green test files (`tests/policy/test_tracer_slice.py`, `tests/state/test_gate_schema.py`).

**Why this plan carries ~20 files (recorded trade-off):** the tracer's whole value is that it touches each layer exactly once. The layers are the DDL, the loader, the catalog, the request/decision types, the evaluator, the admission step, the loop call site, the store writers and the two test lanes; splitting them commits a schema no reader opened, a gate no call path invoked, or a loop insertion no test proved terminal-on-deny. ## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| model output -> batch admission | Provider-produced tool calls enter the registry untrusted; names, args and payload shape are attacker-influenced |
| gate -> backend | Only already-approved, rewritten-args requests may cross into a handler; nothing else may |

| decision store -> logs/transcript | Decision rows, reasons and message rows persist audit data that must never carry a credential |
