# Phase 1 Plan 06: LFS and lockfile import fidelity

**Pointer-grammar verification with a derived, schema-valid LFS inventory, plus a byte-level lockfile check that catches both regenerated bytes and an unlisted Nix/Bazel/Deno lockfile.**

## Accomplishments

- `tools/provenance/lfs.ts` parses the documented pointer grammar (literal version line, lexicographically sorted keys, LF endings, <1024 bytes) and returns a typed error naming the failing line — so an edited `oid` or a reordered pointer is a named finding, not a parse surprise.
- `verifyTree` checks every `tracked[]` record against disk (`missing`, `payload-in-vendor`, `oid-mismatch`, `size-mismatch`, `not-a-pointer`) **and** walks the paths the upstream `.gitattributes` declares: a pointer the inventory omits is `unlisted-pointer`, and a payload there is only accepted when its bytes equal the upstream manifest blob. This is what makes the empty inventory at the pinned commit a proof rather than a skipped check.
- `LFS.json` is now derived by the module (`--write`) and reproduces the committed document byte for byte, so the ledger cannot be hand-edited without a visible diff.
- `tests/provenance/lockfiles.test.ts` re-hashes all 72 listed lockfiles across the four trees, cross-checks each blob OID against both manifests **and** the git index, and prints one `LOCKFILES <tree> <basenames>` line per tree on every run.
- The detector recognises `flake.lock`, `MODULE.bazel.lock` and `deno.lock`, not just npm/Cargo/uv forms; a lockfile-shaped file the ledger omits is reported by name (`undocumented`) instead of being ignored.
- IMPT-06's unclassified edge is discharged as an executed check: the detected basename set is visible on every run, and the fixture suite proves both drift paths bite (corrupted bytes, undocumented file).

## Decisions Made

- **The inventory is derived, never authored.** `--write` is the only writer and its output reproduces the committed file byte for byte; a hand edit therefore shows up as a diff rather than silently redefining "expected".
- **Declared paths are checked even when `tracked[]` is empty.** Driving payload detection from `.gitattributes` as well as from the inventory is the only way to distinguish "upstream tracks no LFS object" from "the inventory forgot one".
- **A payload at a declared path is judged by upstream identity.** `crates/pi-ast/src/language/testdata/ini.wasm` is a real 4710-byte blob committed before the attribute line; it passes because its SHA-256 equals the upstream manifest row, while a fetched payload (bytes ≠ upstream pointer) fails with `payload-in-vendor`.
- **Lockfile completeness is detector-driven.** An empty `lockfiles[]` is legal only when the detector finds nothing; a hard-coded non-empty assertion would have failed a legitimately lockfile-free tree while hiding an unlisted one.
- **Index cross-check added to the manifest comparison.** The plan asked for manifest OIDs; comparing the git index OID as well means rewriting *both* manifests to match a tampered file still fails.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] The plan's `tracked > 0` LFS assertion cannot hold at the pinned commit**
- **Found during:** Task 1 (LFS inventory contract)
- **Issue:** The plan's `<verify><fails_when>` fails the run when the printed `tracked` count is 0, and its `<behavior>` defines `n` as "the number of LFS paths upstream declares". At `0b5c27ab24719c86a5986b95ee55f4e75bc1aaa0`, `git lfs ls-files <sha> --json --long --size` returns `{"files": null}` — upstream deleted the LFS `.wasm` objects when the bindings moved to N-API, leaving the `*.wasm filter=lfs` attribute line stale. A non-zero assertion would therefore be permanently red against a correct import.
- **Fix:** Replaced "non-empty" with "correct and consistent". `--check` asserts that (a) every `tracked[]` record matches its pointer, and (b) every path the upstream `.gitattributes` declares is either a listed pointer or a payload byte-identical to the upstream manifest blob. Success is printed as `LFS OK <tree> tracked=<n> declared=<m> pointers=<p>` — currently `tracked=0 declared=1 pointers=0`, where `declared=1` is the 4710-byte `ini.wasm` proven identical to its upstream blob. `LFS.json` was regenerated through the module and is byte-identical, and a test asserts the declared attribute lines equal the upstream `.gitattributes` at the pinned commit.
- **Files modified:** tools/provenance/lfs.ts, tools/provenance/test/lfs.test.ts, vendor/oh-my-pi/provenance/LFS.json (unchanged bytes)
- **Verification:** `bun run tools/provenance/lfs.ts --tree oh-my-pi --check` → exit 0, `LFS OK oh-my-pi tracked=0 declared=1 pointers=0`; `bun test tools/provenance/test/lfs.test.ts` → 26 pass.
- **Committed in:** `ac636949` (Task 1 commit)

**2. [Rule 2 - Missing Critical] Added `unlisted-pointer` and the declared-glob walk**
- **Found during:** Task 1 (LFS inventory contract)
- **Issue:** The plan's finding vocabulary (`missing`, `payload-in-vendor`, `oid-mismatch`, `size-mismatch`, `not-a-pointer`) only inspects `tracked[]`. With an empty inventory that set can never fire, so the check would pass while proving nothing about the paths upstream declares as LFS.
- **Fix:** `verifyTree` now also walks the tree once, matches each path against the LFS-declared patterns (gitattributes semantics: slashless patterns match the basename at any depth), and reports `unlisted-pointer` for an unlisted pointer or `payload-in-vendor` for a payload that is not the upstream blob. `checkTree` prints the count of declared paths so the reconciliation is visible on every run.
- **Files modified:** tools/provenance/lfs.ts, tools/provenance/test/lfs.test.ts
- **Verification:** tests cover both branches — an unlisted pointer fails, and an upstream payload passes while a fetched payload fails with `payload-in-vendor`.
- **Committed in:** `ac636949` (Task 1 commit)

## Issues Encountered

- The first draft of the out-of-order-key test expected the error at the line of the *previous* key; `parsePointer` points at the offending key itself (line 3 for `size` before `oid`), which is the more useful contract — the test was corrected, not the parser.
- The gitattributes test initially compared the ledger's verbatim lines against extracted glob patterns. The ledger intentionally stores the lines verbatim, so the test now filters the upstream file the same way the deriver does and compares line-for-line.
