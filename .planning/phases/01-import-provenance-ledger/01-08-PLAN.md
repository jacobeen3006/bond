<objective>
**As a** maintainer, **I want to** detect ledger drift offline on every commit and see exactly which path, mode, or patch order broke, **so that** the ledger cannot rot between imports.

Purpose: a ledger is true exactly as long as something fails when it stops being true. `verify` is the cheap always-on gate; replay is the expensive reconstruction. This plan makes the cheap gate real and makes the expensive one's failure modes explicit.

Output: `tools/provenance/verify.ts`, the three drift suites, and a pre-commit hook that runs the cheap gate.

Scope note (estimate 105k vs the 100k advisory budget, confidence low): no split is taken. `verify` and `replay` share the manifest reader and the `isLedgerPath` predicate; splitting them would let the two gates drift apart, which is the failure this plan exists to prevent.
</objective>

  <action>
Write `tools/provenance/verify.ts` with a main guard (`bun run tools/provenance/verify.ts [--all|--tree <name>]`). For each subtree it: (1) reads `UPSTREAM.json`, `EXCLUDES.json`, and both manifests, and asserts `repo` matches `^https://`; (2) recomputes the SHA-256 of each manifest file and of `EXCLUDES.json` and `RENAMES.json` and compares them to `manifests.upstream_sha256`, `manifests.vendored_sha256`, `excludes_sha256`, and `renames_sha256` — drift in an exclude or rename map is exactly as invisible as manifest tampering, so all four digests are recomputed here, not only the two manifests; (3) compares `git ls-files -s -- vendor/<tree>` against `MANIFEST.vendored.tsv` by mode, blob OID, and path — filtering both sides through `isLedgerPath()` from `manifest.ts`, so a `provenance/` file is never a comparison row and a correctly imported tree does not report its own ledger as `ADDED`; (4) hashes each working-tree file with raw bytes and compares to the manifest SHA-256 — for a mode `120000` path, hash the blob bytes from `git cat-file blob <oid>` (the stored link text), never the worktree materialization, because a clone with symlinks materialized would otherwise always report `MODIFIED`; (5) validates each ledger file's existence and parses it (a missing or unparsable ledger is `MISSING`, never a skip); (6) asserts excluded paths are absent; (7) asserts no `.git` directory, no `.gitmodules`, and no mode `160000`.

Failure output is one line per finding using a fixed vocabulary: `MODIFIED`, `ADDED`, `REMOVED`, `MODE`, `TAMPERED`, `MISSING`, `EXCLUDED-PRESENT`, `GITLINK`. Print at most 200 lines then `... <n> more`. Exit 1 when any finding exists, 2 on a malformed ledger, 0 when clean. No `git fetch`, no `cat-file` against `upstream-cache/`, no network call of any kind: `git cat-file blob` reads the local object database of the repository being verified and is allowed; this runs on every commit (DEC-02).

Add the unrecorded-edit detector as a distinct function `findUnrecordedEdits(tree, patchSeries, upstreamManifest, vendoredManifest)`: every path whose vendored OID differs from `MANIFEST.upstream.tsv` must be named by at least one patch file in `series` (parse the `diff --git a/<path> b/<path>` lines of each listed patch). A differing path absent from every patch is reported as `UNRECORDED <path>`, which is the detector PITFALLS P-10 describes. Series entries are parsed in order and no patch is applied here.

`tests/provenance/unrecorded-edit.test.ts` builds the hermetic fixture, imports it, then: (a) modifies a vendored file directly and asserts `UNRECORDED <path>` plus exit 1; (b) reverts it, generates a real patch through the documented flow, appends it to `series`, regenerates the vendored manifest, and asserts `UNRECORDED` disappears and exit is 0; (c) deletes a ledger file and asserts exit 1 with `MISSING`.

| Boundary | Description |
|----------|-------------|
| working tree → ledger | A hand edit reaches the commit unless something compares it |
| manifest → verification verdict | A forged manifest digest would excuse every downstream difference |
| developer machine → CI | A local-only gate is bypassed by anyone who does not install it |
